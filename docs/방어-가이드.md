# 방어 가이드

대상은 웹·API 를 운영하는 팀과, 내부에 LLM 에이전트를 두는 팀이다. ARTEX 라는 이름에 맞추기보다, 공개 소스가 보여 준 요청 형태가 통과하지 못하게 막는 쪽에 둔다.

지표 일치만으로 침해를 선언하지 않는다. 지표가 없어도 조사를 끝내지 않는다. 2026년 10월 금융권 보도와 ARTEX 의 연관은 이 글을 쓰는 시점에 공식 확인 전이다. PLURA 는 후보 User-Agent 를 사건 로그로 검증하지 않았다고 밝혔다.

## 1. 속도 제한

고정 수집 스크립트는 JS 를 한꺼번에 받고, HTML 순회 기본 지연은 0.1초이다. LLM 이 만든 클라이언트는 그보다 느릴 수도, 헤더가 없을 수도 있다. 그래서 User-Agent 룰만 걸지 말고 주체별 속도를 제한한다.

- 인증 전 경로와 인증 후 경로의 한도를 나눈다. 로그인 전 조회는 더 낮게 둔다.
- 한도 키는 IP 만 쓰지 않는다. 계정, 세션, 토큰, 대상 리소스 식별자를 같이 본다. NAT 와 사내 프록시 뒤에서 IP 한도는 정상 사용자를 같이 막는다.
- 초과분은 429 와 재시도 시각을 주고, 일정 시간 같은 조회의 성공 응답을 줄인다.
- WAF 의 속도 제한과 애플리케이션 한도가 둘 다 필요하다. WAF 는 엣지에서 자르고, 애플리케이션은 "이 계정이 이 고객 번호를 몇 번 봤는가"를 안다.
- 한도 값은 사이트의 정상 피크로 정한다. 이 저장소의 휴리스틱 기본값(JS 20개, API 경로 25종, 조회 값 8종)은 탐지 시작점이지 차단 임계가 아니다.

## 2. 조회 API 의 서버측 인가

번호만 바꿔 다른 사람 정보가 나오면 User-Agent 룰은 의미가 없다. PLURA 가 경로 이름 대신 접근 행위를 보라고 한 이유다.

- 모든 조회는 서버에서 주체와 대상의 관계를 확인한다. 화면에서 버튼을 숨기는 것으로 끝내지 않는다.
- 식별자는 추측하기 어려운 값을 쓰거나, 추측 가능한 번호라면 소유 검사를 빼먹지 않는다.
- 목록 API 가 권한 밖의 식별자를 반환하지 않는지 본다. 상세 조회만 막으면 목록이 새 번호를 알려 준다.
- 응답 필드를 역할별로 줄인다. 오류 본문에 내부 경로, SQL, 스택을 넣지 않는다.
- 직원용·협력사용·민원용처럼 인증이 약한 보조 시스템을 같은 기준으로 다시 본다. 본 서비스만 점검하면 빠지는 면이 이쪽에 많다.

## 3. 봇 관리

세 User-Agent 는 후보 시그니처로 등록하되, 봇 관리의 전부가 아니게 한다.

- 알려진 점검·모니터링 대역은 예외로 두고 나머지에 탐지를 건다. 바로 차단하지 말고 탐지 전용으로 하루 이상 본다.
- 좋은 봇(검색, 모니터링, 파트너)은 공개 IP 와 역방향 확인으로 구분한다. User-Agent 문자열만 믿지 않는다.
- 헤더가 없는 클라이언트, 헤드리스 브라우저, 아주 짧은 간격의 순회를 위험 점수로 더한다. 그 점수만으로 차단하지 않는다. 인증 상태, 대상 경로, 응답이 달라지는지를 같이 본다.
- JS 챌린지는 브라우저 수집에는 도움이 되고, 단순 HTTP 라이브러리에는 효과가 있다. 챌린지를 통과한 뒤의 인가 부재는 막지 못한다.
- `artex-selfupdate` 는 들어오는 웹 요청용 룰에 넣지 않는다. 내부 프록시에서 설치 탐지용으로만 본다.

Sigma, Suricata, ModSecurity 예시는 `rules/` 에 있다. ModSecurity 예시는 `pass,log` 이다.

## 4. 노출 면 줄이기

- 외부에서 열리는 URL·API 목록을 갱신한다. 개발, 스테이징, 협력사, 민원, 모바일 웹뷰를 포함한다.
- 쓰이지 않는 관리 경로와 디버그 엔드포인트를 끈다.
- 프런트 번들에 내부 API 지도가 그대로 있지 않은지 본다. 번들을 읽는 수집은 인증 없이 경로 이름을 얻는다. 비밀은 번들에 넣지 않는다. 경로 이름이 드러나는 것 자체보다, 그 경로의 인가가 중요한 이유다.
- 오류 페이지, 디렉터리 목록, 소스맵, 백업 파일을 끈다.
- 콘솔형 관리 도구를 인터넷에 두지 않는다. 두어야 하면 VPN 또는 제로트러스트 뒤에 두고, 기본 포트만 믿고 숨기지 않는다. 8787 은 ARTEX 기본값일 뿐 다른 프로그램도 쓴다.

## 5. LLM 에이전트와 도구 실행

조직이 자체 에이전트를 돌린다면, 피해자가 되기 전에 운영자로서 막을 일이 있다. ARTEX 구조는 플래너가 의도를 내고 워커가 도구를 실행한다. 그 패턴을 사내에 둘 때의 통제이다.

- 도구 허용 목록을 둔다. 셸, 임의 HTTP, 브라우저 구동은 기본 거부하고 필요한 도구만 연다.
- 에이전트 네트워크는 업무망과 분리하고, 나가는 주소는 프록시에서 허용 목록으로 막는다.
- 프로덕션 자격 증명, 고객 데이터, 관리자 토큰을 에이전트 환경에 넣지 않는다.
- 사람이 승인하기 전에는 상태 변경과 대량 조회가 나가지 않게 한다. 승인 기록을 남긴다.
- 모델에 넣는 업무 데이터와 도구 결과를 구분하고, 보존 기간을 둔다.
- 사내 모의 점검은 범위, 시간, 대상, 속도, User-Agent 를 미리 보안 팀에 알린다. 그래야 이 키트의 탐지와 구분된다.

이 통제는 공격 절차를 막는 운영 정책이다. 특정 도구를 켜는 방법이 아니다.

## 6. 탐지가 나온 뒤

1. 인가된 점검·모니터링인지 먼저 확인한다.
2. 출발지, 시각, Host, 메서드, 전체 경로, 쿼리, User-Agent, 계정, 응답 코드를 한 표로 모은다.
3. 같은 주체의 앞뒤 요청을 붙인다. 지표 한 줄만 보지 않는다.
4. 조회가 권한 밖의 데이터에 닿았는지 애플리케이션 로그로 확인한다. WAF 에 문자열이 보인 것과 데이터가 나간 것은 다르다.
5. 내부에서 `artex` 프로세스, `autumn27/artex` 이미지, 콘솔 제목이 있는지도 본다. `artex-hunt host` 는 넘겨받은 디렉터리와 프로세스·컨테이너 목록만 읽는다.
6. 차단은 확인된 비인가 출발지와 남용된 자격 증명부터 한다. User-Agent 전체 차단은 오탐 검토 뒤에 한다.
7. 유출 범위가 있으면 아래 신고 시계를 따른다.

`artex-hunt` 는 로그 파일을 읽는다. 라이브 트래픽을 가로채거나 상대를 스캔하지 않는다.

## 7. 신고

긴급 상담은 한국인터넷진흥원 118 이다. 국번 없이 118, 해킹·바이러스 긴급 상담은 ARS 2번, 연중 24시간이다. 안내 페이지: https://www.kisa.or.kr/118

온라인 침해사고 신고는 인터넷침해대응센터(보호나라) https://www.krcert.or.kr 의 상담·신고를 이용한다. 전화는 같은 118 이다.

개인정보가 유출된 경우 침해사고 신고와 개인정보 유출 신고는 별도다. 개인정보보호위원회·KISA 신고 기한은 사안별로 72시간 이내 또는 즉시인 경우가 있다. 개인정보침해 신고센터는 https://privacy.kisa.or.kr 이고 전화는 118 이다. 해당 조문과 기한은 신고 전에 최신 안내로 확인한다.

금융회사는 118 과 함께 금융보안원 등 업권 비상대응과 사내 규정된 보고 선을 탄다. 업권 창구의 주소와 양식은 회사가 이미 받은 공식 채널을 쓴다. 이 글은 그 창구를 대신 적지 않는다.

경찰 수사가 필요한 경우 사이버수사국 등 수사기관 신고를 병행한다.

외부에 넘기는 묶음에는 고객 원문, 토큰, 세션 값을 넣지 않는다. 시각, 출발지, 대상 호스트, 경로 패턴, 건수, 이미 가린 증거면 충분하다.

## 8. 하지 말 것

- 후보 User-Agent 일치만으로 침해 성공을 발표하지 않는다.
- 세 문자열이 없다고 안전하다고 하지 않는다.
- `/api/` 를 ARTEX 전용 경로로 차단하지 않는다.
- 8787 포트만으로 호스트를 악성으로 단정하지 않는다.
- `artex_token` 을 대외 웹사이트의 쿠키 차단 룰로 옮기지 않는다.
- GitHub 를 `artex-selfupdate` 때문에 악성 목적지로 막지 않는다.
- 공개되지 않은 IP 를 추정해 차단 목록으로 퍼뜨리지 않는다.
